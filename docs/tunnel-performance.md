# 隧道传输优化与本机测量

2026-09-23，Windows/amd64，Intel i5-10400F（12 逻辑 CPU），Go 1.26.5。修改前后使用同一工作区、同一组基准，顺序运行，每组重复三次；下表取中位数。真实网络测试使用本机 TCP socket、TLS 1.3 和回显目标。

AES-GCM 算法加解密、硬件/软件实现对照及四承载持续上传/下载的补充测量见 [AES 与隧道基准](aes-tunnel-benchmark.md)。

## 已实现

- 帧头和载荷合并成一次底层写入。WSS 一帧对应一个二进制 WebSocket 消息，减少小写入；帧写缓冲和双向中继的 32 KiB 缓冲由 `sync.Pool` 复用。
- TCP 帧直接读入调用方缓冲，保留未读长度，避免每帧分配整个载荷并再次复制。小缓冲读取、半关闭、空 UDP 包及数据边界保留；`ReadPacket` 返回的数据仍独立归调用方所有。
- Mux 全局锁只保护连接池元数据；网络拨号、开流和关闭连接都在锁外进行。同一协议、地址、证书名称、Token 的并发拨号共用一次建连，各调用方独立取消。仍限制 64 条承载连接、每条最多 256 个活动或正在创建的流，未完成拨号也计入上限。关闭连接池会取消未完成拨号并阻止回填。
- Agent 的信任配置共享有界 TLS 会话缓存。出口对同一监听器复用 TLS 配置，让 Go 自动管理和轮换会话票据密钥。恢复握手后仍执行隧道 Token 和目标鉴权，TLS 1.3、证书验证要求不变。
- WAL 合并当前队列中已到达的计量请求并立即提交，移除每批固定的 1 ms 收集等待。每批最多 128 条、队列 256 条、待确认记录 4096 条的边界不变；只有 `fsync` 成功后才返回允许发送，配置/确认/退租操作仍保持队列顺序。

这批修改兼容现有数据帧格式，无需调整面板规则。入口、链路中转和出口需运行重新构建的 Agent，才能在相应方向获得优化；重启面板本身不会替换已部署节点的 Agent。

## 测量结果

纯帧读取，32 KiB 一帧：

| 指标 | 修改前 | 修改后 |
|---|---:|---:|
| 平均耗时 | 4763 ns | 710 ns |
| 每次分配 | 32773 B / 2 次 | 0 B / 0 次 |

合并写入需要复制载荷，因此写向 `io.Discard` 的纯内存基准从约 41 ns 增至 706 ns；它省略了实际要减少的 TLS/WebSocket/系统调用开销，应结合真实承载测量判断。

四承载的持久连接每次发送并回显 32 KiB，**不含 Agent 计量、首次握手和建连时间**。MB/s 按单方向载荷计算，每次操作实际还接收同量回显。分配量包括同进程内出口和客户端的工作。

| 承载 | Mux | 修改前 MB/s | 修改后 MB/s | 修改前 B/op | 修改后 B/op |
|---|---|---:|---:|---:|---:|
| TLS | 关 | 301.93 | 296.11 | 66943 | 639 |
| TLS | 开 | 199.45 | 235.80 | 70761 | 2390 |
| WS | 关 | 203.50 | 201.36 | 67686 | 998 |
| WS | 开 | 150.52 | 173.57 | 71280 | 2941 |
| WSS | 关 | 199.13 | 215.55 | 67368 | 712 |
| WSS | 开 | 153.42 | 176.16 | 71404 | 2740 |
| HTTP CONNECT | 关 | 275.94 | 364.52 | 67005 | 329 |
| HTTP CONNECT | 开 | 201.90 | 232.87 | 69992 | 2244 |

内存分配下降明确；各承载吞吐变化不一致，TLS/WS 关闭 Mux 的中位数略低。HTTP 与 TLS 的持续数据路径基本相同，本轮吞吐差异包含运行波动，不能据此宣称 HTTP 比 TLS 更快。Mux 表内收益来自帧路径优化；跨节点锁隔离由并发回归验证，这张表并未测量连接风暴。

真实磁盘 WAL 计量，每次扣除 32 KiB，512 次操作：

| 指标 | 修改前 | 修改后 |
|---|---:|---:|
| 单工作协程平均每次耗时 | 2.066 ms | 0.560 ms |
| 单工作协程 P95 | 2.992 ms | 0.998 ms |
| 32 工作协程总耗时 / 操作数 | 63.88 μs | 35.28 μs |
| 32 工作协程单次请求 P95 | 2.992 ms | 1.995 ms |
| 32 工作协程平均每次同步的计量数 | 32 | 16 |

取消定时收集降低等待，也可能增加同步次数，本机 32 并发即出现此取舍。磁盘较慢时需重新测量。Windows 本次逐请求时钟样本约以 1 ms 跳变，P95 及基准输出的 `fsync-us` 只供粗粒度定位，不能据其分解精确磁盘延迟；总体平均时间使用 Go benchmark 计时。

这些是开发机微基准和回环测试，不是公网速率、Linux 双机容量或带丢包线路的验收，也未包含限速、租约更新及控制面上报的完整链路。

## 复现与验证

```sh
go test ./internal/tunnel -run '^$' -bench '^BenchmarkSessionFrames$' -benchmem -benchtime=300ms -count=3
go test ./internal/tunnel -run '^$' -bench '^BenchmarkCarrierRoundTrip$' -benchmem -benchtime=1000x -count=3
go test ./internal/agent -run '^$' -bench '^BenchmarkChargeLatency$' -benchmem -benchtime=512x -count=3
go test -race ./internal/tunnel ./internal/agent ./cmd/agent -count=1
```

计量基准使用隔离的临时状态目录、实际落盘，并在计时区间外确认用量，避免长时间运行碰到待确认队列上限。原始本机输出位于 `.local/{frames,carriers,charge}-{before,after}.txt`，不纳入版本控制。

回归覆盖旧帧字节格式与短写、小缓冲和截断帧、WSS 消息合并、四承载 TCP/UDP 实传、TLS 会话恢复和拒绝无效凭据、同目标 32 并发共用承载、慢目标隔离、取消等待、阻塞开流超时、连接池关闭，以及 WAL 并发预算、同步前不放行和崩溃恢复。

后续在目标 Linux 主机上按实际带宽、RTT 和丢包率测量，再决定 Mux 窗口、多承载分流及心跳参数。本文记录的 2026-09-23 性能优化不包含租约切换；2026-09-24 的后续实现见 [流量连续性修复](traffic-continuity.md)。UDP/QUIC 和异步额度预留涉及协议或账务语义，仍未引入。

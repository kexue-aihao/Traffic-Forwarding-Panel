# TCP 额度控制延迟优化

2026-10-11，v0.1.46 在正式版 v0.1.45 基础上优化单连接与多连接在额度续接时的等待；目标仍为单连接持续 2 Gbps、突发 3 Gbps，多连接不增加统一速率上限。安装包及升级注意事项见 [发布说明](releases/v0.1.46.md)。

v0.1.46 之后针对控制请求抖动的持续传输优化，见 [TCP 抖动与续接说明](tcp-jitter-performance.md)。

## 原因与修改

此前的吞吐基准使用固定大租约，能验证数据路径和 WAL 同步开销，但不能验证商用面板不断分配下一额度时的等待。本轮新增实际 Go 控制面、SQLite 商用分配器和 Agent 的持续下载回归，将每个 Agent HTTP 请求额外延迟 60 ms 或 240 ms，覆盖配置、ACK、用量、预取及退租。

- 速率估计原来每次观察乘以 0.8。每 100 ms 检查一次时，连续几个控制请求就会使需求估计大幅降低，下一额度随之缩小。改为按实际经过时间衰减，时间常数五秒；首次有消费时使用活跃窗口的开始时间，避免启动前的空闲压低估计。
- 加载缓存授权配置后，预取与用量结算立即独立运行。它们此前要等首次配置 GET/ACK 结束，有限的初始 16 MiB 额度可能已耗尽。
- 配置锁只保护应用配置与获取 ACK 状态，HTTP GET/ACK 在锁外运行。延迟的 ACK 不再挡住备用额度生效；晚到的旧 GET 使用当前持久化配置进行 ACK，避免覆盖已经应用的新版本。
- 新 Agent 对预取与退租请求发送可选 `X-TFP-Lease-Config: 1`。新面板可以在操作提交后同时返回完整授权配置，省去等待下一次 GET 才能使用额度的时间。使用普通配置接口的同一个快照编译器，Agent 仍执行身份、策略、租约和持久化校验；正常配置工作协程负责 ACK。
- 正在预取时，低余额本身不会触发主额度退租。写入退租 WAL 前再次检查当前规则，解决列出待退租额度后才开始预取的并发窗口；配置或租约即将到期仍照常退租。
- 已确认退租、没有可提升的备用额度时，支持流水预取的节点按前一额度预算申请有限替代额度，避免活跃传输反复回到 16 MiB。过期空闲额度不沿用这条路径。

旧面板忽略可选请求头，仍返回原有 `lease_id` 或 HTTP 204；新 Agent 回退到正常配置轮询。旧 Agent 没有请求头时，新面板保持原响应。若附带配置生成失败，面板保留已经提交的操作结果，后续轮询重试。

## 三轮对照

Windows amd64、Intel i5-10400F、Go 1.26.9，同一台机器顺序运行正式版 v0.1.45（`fe7cc4aaf7758462c2cd090215a8bbade8fd1912`）与修改版。每个场景下载 512 MiB，单条规则使用一个或八个连接，共用额度；初始额度为 16 MiB。测试只将隔离账户配额扩大至 4 GiB，后续分配、用量确认、退租和预留回收全部经过实际商用账本。TLS Mux 场景同时启用真实 TLS 和 `random-padding`。

| 路径 | 控制延迟 | 连接数 | v0.1.45 均值（Gbps） | 修改版均值（Gbps） | 修改版三轮范围（Gbps） | 每轮最大读取间隔范围，旧 → 新（ms） |
| --- | --- | --- | --- | --- | --- | --- |
| direct | 60ms | 1 | 5.335 | 6.434 | 6.050–6.912 | 227–232 → 55–62 |
| direct | 60ms | 8 | 5.755 | 8.810 | 8.463–9.150 | 225–299 → 60–75 |
| direct | 240ms | 1 | 0.923 | 2.824 | 2.777–2.859 | 950–963 → 668–725 |
| direct | 240ms | 8 | 1.138 | 2.749 | 2.204–3.025 | 954–1195 → 795–827 |
| tls-mux | 60ms | 1 | 3.104 | 3.501 | 3.375–3.602 | 206–210 → 46–48 |
| tls-mux | 60ms | 8 | 5.015 | 5.492 | 5.245–5.780 | 215–222 → 50–68 |
| tls-mux | 240ms | 1 | 1.076 | 2.853 | 2.793–2.905 | 931–968 → 217–227 |
| tls-mux | 240ms | 8 | 1.082 | 2.810 | 2.666–3.094 | 961–963 → 726–980 |

计时包含缓存规则开始传输时与 Agent 首次配置 GET/ACK 重叠的阶段。读取间隔包含各连接等待数据的时间，不等于 TCP 断开。高于目标速率的回环路径仍可耗尽有限额度，不能据平均吞吐宣称消除了所有停顿。所有场景逐字节校验载荷，并核对下载 512 MiB 加每连接一个上传标记的计费总量；没有使用易波动的吞吐断言。

原始本地输出保存在 `.local/tcp-latency-20261011/baseline-final.txt` 和 `optimized-final.txt`。可复现命令：

```sh
go test ./internal/integration -run '^TestTCPDownloadAcrossControlPlaneLatency$' -count=3 -v -timeout=5m
```

另对 240 ms 控制延迟运行每场景 2 GiB 的单轮对照，检查更多次额度续接。初始额度、分配器和计费核对相同，隔离账户配额仍为 4 GiB；这不是 30 秒或 24 小时验收：

| 路径 | 连接数 | v0.1.45（Gbps） | 修改版（Gbps） | 最大读取间隔，旧 → 新（ms） | 退租请求次数，旧 → 新 |
| --- | --- | --- | --- | --- | --- |
| direct | 1 | 0.938 | 2.818 | 965 → 956 | 22 → 8 |
| direct | 8 | 1.352 | 2.953 | 952 → 871 | 17 → 9 |
| tls-mux | 1 | 1.619 | 2.462 | 967 → 695 | 11 → 8 |
| tls-mux | 8 | 1.212 | 3.272 | 961 → 819 | 19 → 8 |

修改版的下载计时约 5.25–6.98 秒，旧版约 10.61–18.31 秒。更大的传输量仍有提升，但最大等待没有完全消除，尤其直连单连接的最坏一次读取间隔改善有限。原始输出为同目录下的 `baseline-sustained.txt` 与 `optimized-sustained.txt`。测试支持 `TFP_TEST_TCP_DOWNLOAD_MIB`（512–4096 MiB），复现此组对照：

```sh
TFP_TEST_TCP_DOWNLOAD_MIB=2048 go test ./internal/integration \
  -run '^TestTCPDownloadAcrossControlPlaneLatency$/^(direct|tls-mux)_240ms_[18]streams$' \
  -count=1 -v -timeout=6m
```

这是控制 HTTP 请求延迟模拟，数据面使用回环网络，未模拟公网 TCP RTT、丢包或跨机带宽。截图中 HTTPS 测速延迟不能直接当作 Agent 到面板的请求延迟，也不能仅凭截图确认线上瓶颈。截图中的测速目标标注 2000M，突发 3 Gbps 的验收需要有更高容量的目标和完整链路。

## 验证与使用范围

本地 `go test -race ./... -count=1 -timeout=10m`、`go vet ./...`、Go 格式和 `git diff --check` 均通过。全仓竞态检查覆盖 Agent、平台、商业账本和真实传输集成；随后扩展的 1、1/2、3/2 计费倍率专项也在 race 下通过，核对替代额度的实际计费预留及已退额度的精确回收。阻塞首次 ACK、晚到配置、错误节点身份、预取期间退租与授权即将到期的回归均通过。

OpenAPI 重新生成后哈希一致，146 个操作的文档包括可选请求头与配置响应。面板和 Agent 的 `CGO_ENABLED=0` Linux amd64/arm64 构建通过。本轮本机使用 SQLite；Linux 全仓 race、PostgreSQL/MySQL、systemd/升级监督进程、HTTPS、浏览器和双架构 Docker 验证以 v0.1.46 的 GitHub Actions 结果为准。公网跨机性能尚未验收。

全部效果需要更新面板和 Agent；仅更新 Agent 时，旧面板上的内联配置优化不会启用。这次没有数据库迁移或 WAL 格式变化；每份分配的计费预算仍最多 256 MiB，账户总在途计费预留仍最多 512 MiB，TCP WAL 每规则/账户每 Agent 的责任仍最多 4/8 MiB。套餐资源限制、到期和撤销、先落盘后转发仍生效。Linux socket 继续继承机器现有的拥塞控制设置，包括 BBR。

公网验收应核对入口、每级中转及出口的实际运行版本，使用同一客户端与目标对比绕过转发的单连接速度，记录承载、Mux、混淆、套餐限制、CPU、磁盘同步延迟、Agent 到面板的请求耗时、数据面 RTT 和丢包。单连接和多连接各至少运行三轮、每轮 30 秒并保留每秒速率和错误日志；本地结果不代表所有机器已达到目标。

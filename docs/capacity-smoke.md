# 三库计量热路径冒烟记录

2026-09-20至21，本机Windows、12逻辑CPU、约32GiB RAM；数据库与负载生成器共用开发机。SQLite使用WAL/FULL，PostgreSQL18.6、MySQL8.4.6保留本机持久化配置。以下是开发实验，不是16vCPU/32GiB/NVMe加独立压测机的容量验收。

```sh
go test ./internal/platform -run '^$' -bench '^BenchmarkUsageCapacity$' -benchtime=500x -count=1
```

每次创建隔离数据库，种子包括500节点、10,000用户、100,000规则及有限商业租约；500个计量批次，每批200条，全部100,000规则各产生一条真实计量记录。种子时间不计入ns/op；控制面用量、商业用量与权益used总数逐一断言相等，预期各100,000事实/102,400,000字节。依次运行，没有同时运行其他代理的构建/测试。

| 数据库 | 纳秒/批（200条） | 记录/秒 | B/op | allocs/op | 对账 |
|---|---:|---:|---:|---:|---|
| SQLite | 19,158,569 | 10,439 | 2,460,406 | 23,094 | 通过 |
| MySQL8.4.6 | 173,242,618 | 1,154 | 2,788,517 | 22,501 | 通过 |
| PostgreSQL18.6 | 31,115,576 | 6,428 | 4,445,651 | 24,863 | 通过 |

这些数字只覆盖串行调用的SQL计量事务，不包含HTTP链路、150读/20写/5财务每秒、500实时订阅、探针聚合/清理、满留存、节点重连或磁盘故障。100,000活跃规则每10秒上报意味着平均10,000事实/秒：PG/MySQL本轮串行批次未达到这个速率，SQLite也没有证明混合负载下仍有足够余量。不能凭事务对账通过或一次瞬时吞吐宣称P1通过。

后续在完整负载下测批大小与调度、队列延迟和错误率，定位SQL往返、锁等待、日志同步与索引开销；三库仍保持同目标规模，不以缩小SQLite数据集通过验收。
